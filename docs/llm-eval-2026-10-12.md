## Tuning changes attempted (folded into `buildGenerationPrompt`)

P2.5 showed the stock prompt under-specifying the rule language; the following changes were
made before iteration 1, and they held without further iteration:

1. **Condition union spelled out** — the prompt now lists every legal `if` shape
   (`and`/`or`/`not`/`has`/`hasTag`/comparisons), the legal comparison `ValueRef` forms
   (including `{"stat":"objective.<id>.progress"}`), and explicitly bans bare
   `{"entity": ...}` condition objects in favor of `{"op":"has", ...}`.
2. **Action catalog with exact fields** — every action type is enumerated with its required
   keys; `showMessage` is documented as `text` (not `message`); invented types such as
   `stateChange` are banned, and event names are not valid actions.
3. **Entity state enum** — `state` restricted to `idle|patrol|chase|return`.
4. **Winnability patterns** — the engine never advances objectives on its own, so the prompt
   now requires concrete progress rules (`playerEnter` zone triggers for collectibles,
   `interact` triggers for switches, `playerEnter` for reach zones), `count` on every
   progressable objective (1 for reach, one per target otherwise), and a
   `win` action on `objectiveComplete` for every objective.
5. **Open-ground layout constraints** — empty `terrain.obstacles` unless the user asks for
   obstacles; if obstacles exist, keep them clear of the spawn→target lines.
6. **Few-shot rewrites** — all four archetype examples now demonstrate the progress/complete/win
   rule chain, target zones co-located with collectibles, explicit `count`, and empty obstacle
   lists (the previous examples contained collect/reach objectives that no rule could ever
   complete).

No schema, engine, pipeline, or repair changes were made to compensate for prompt issues.

Auto-play verification used a temporary steering harness (not committed; P2.8 owns the real
`tests/helpers/steer.ts` + `tests/playtest.test.ts`): for each collect/activate objective it
steered to every target in order (pressing interact for activate targets) and asserted
`getState().status === "won"` within the tick budget. Results:

```
live-open-collect.json: won=true
live-open-puzzle.json:  won=true
live-puzzle-beams.json: won=true
```

Every generated collect target has a co-located `zone` entity plus a `playerEnter` rule that
despawns the collectible and calls `objectiveProgress`; every activate target has an `interact`
rule; every objective has `count` and a `win` rule on `objectiveComplete`. This is exactly the
structure P2.8's deterministic steer helper needs.
