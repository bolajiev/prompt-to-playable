## Offline playtests (no network)

The walkthrough test exercises real movement (away ≥2.5 units and back into the door's 3.5-unit `interactRange`) and asserts door travel in both directions plus the `doorOpen` scratch toggle; it keeps the static check that the door's interact rules include a slide/`openDoor` action.

## Tool changes folded into `scripts/llm-smoke.ts`

1. Prompt entries accept optional `expectMode` (validated against `GameModeSchema`, reported as `MODE_MISMATCH`) and optional `fixture` (an explicit `tests/fixtures/<name>.json` capture target).
2. `--capture-fixtures` writes only entries that declare `fixture`, so a `--no-write` eval can still capture named playtest docs without touching `live-*.json`.
3. A per-mode kit gate prints `usable=<kit>` (`inspect`/`walkthrough`/`drive`/`game`/`explore`) or `usable=none` with a gate failure class (`INSPECT_NO_CONTENT`, `INSPECT_NO_CLICK_RULE`, `WALKTHROUGH_NO_PLAYER`, `WALKTHROUGH_NO_INTERACTABLE`, `DRIVE_NO_VEHICLE`, `DRIVE_CHECKPOINTS_LT3`, `DRIVE_NO_WIN`, `EXPLORE_ZONES_PRESENT`), plus `mode=<meta.mode>` on the result line.
4. The summary line adds a `kits=[...]` tally; explore scenes now require 0 zones to be `explorable`.

## Honest assessment

**What works.** All 15 prompts landed on the expected kit/mode and produced schema-valid documents (13/13 generations, 2/2 edits), with one repair request total. Both PCB prompts routed to inspect even though only one contains explicit inspect vocabulary, both walkthrough prompts routed to walkthrough (including the house prompt, which contains the goal word "door"), and both race prompts routed to drive. The kit few-shots carried parts/labels/panels, door/lamp interactions and ordered checkpoint rules into the live documents. Offline, the captured inspect fixture opens a panel on click, asserts the rule's `setColor` and applies it; the walkthrough fixture is walked away from and back to the door before two interacts open and close it; and the captured race fixture — an oval with a solid 30x30 infield — is won by simple throttle + pursuit with reverse recovery, proving the drive kit is actually winnable through its rules and not merely carrying a `win` action.

**What's shaky.**

1. **Door toggle semantics were fixed after this eval.** At capture time the engine evaluated rule conditions against live state within a single pass, so the sample's paired open/close rules both matched one press and the door ended closed. Commit `1b843d6` made rule evaluation two-phase (conditions read pass-start state, matched actions apply in rule order), so each press now fires exactly one toggle branch. The fixture was not re-captured: the `kit-house` playtest walks away from the door, returns, and asserts the first press opens it (travel > 0.5, `doorOpen=1`) and the second closes it (travel < half, `doorOpen=0`). This caveat is therefore obsolete for the engine and the committed doc.
2. **One sample per prompt.** Temperature is 0.2 but generation is stochastic; one green run does not prove these exact documents reproduce on a judge's machine. The three committed fixtures pin the playtests to this run's samples.
3. **`open the door wider` shows no structural change** in the diff line; the patch tool reports entity/objective/rule deltas only, so value-level edits (for example the slide `to` vector) are invisible in the report. The edited doc was not captured.
4. **"Usable" is static for inspect/walkthrough.** The playtests simulate only the three captured fixtures; the other 12 entries were checked by schema/sanity/kit gates, not by a scripted playthrough.
5. **Latency tail.** 4.4 s – 137.7 s per invocation; the platformer generation at 137.7 s is far past comfortable demo latency. The gateway was stable (0 transient retries).
6. **`EXPLORE_ZONES_PRESENT` is new.** Explore fixtures that existed before this eval would now fail the label; the repo's committed explore output has no zones, so no committed asset changed.
