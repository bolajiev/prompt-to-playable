# Live LLM Eval — 2026-10-14 (Task 6, judge-style prompts)

**Model:** `deepseek-v4.1-flash`
**Endpoint:** OpenAI-compatible chat completions via the opencode go gateway (`OPENAI_BASE_URL` in `server/.env`; URL and key not recorded). The gateway's `X-Session-Id` header is configured (`OPENAI_SESSION_ID`).
**Command:** `npx tsx scripts/llm-smoke.ts --prompts scripts/prompts-judge.json --no-write`
**Pipeline:** stock classifier + generator + up to 2 repairs; no smoke-side prompt guidance.
**Prompt set:** `scripts/prompts-judge.json` — 10 judge-style prompts: 4 game (one per archetype), 4 explore/scene, 2 conversational edits. Each entry records `expectArchetype`; a mismatch is reported as `ARCHETYPE_MISMATCH`. The two edit entries name their base document with `editOf` (`judge-edit-guard` → `judge-stealth`, `judge-edit-crystals` → `judge-forest`).
**Iterations used:** 1 of 3. All 10 prompts passed on the first run; no tuning was required. A second, edit-only verification run re-generated the two edit bases and re-applied the two edits so the tool could print a structural diff of the patch result.
**Tuning changed:** none. No classifier, generator, few-shot, schema, sanity or edit-prompt change was made.
**Fixtures:** not written (`--no-write`); `tests/fixtures/` stayed byte-identical (committed capture set from P2.6 is unchanged).

## Tool changes folded into `scripts/llm-smoke.ts`

1. `--prompts` entries accept optional `expectArchetype` (validated against `ArchetypeSchema`) and `editOf` (marks a conversational edit and names its base slug). Default runs keep the P2.6 capture set and its single edit.
2. Explore documents report `explorable=<bool>` instead of `solvable=<bool>`; the summary line gains an `explorable=<count>` field.
3. Game documents are checked with `hasWinPath` in addition to `sanityCheck` (same "usable" semantics as `eval:corpus`); explore documents with objectives are reported as `OBJECTIVES_PRESENT`.
4. Generation rows print `stats: entities=… objectives=… rules=…`; edit rows also print an `edit-diff` line (added/removed entity ids, objective/rule deltas).

## Honest assessment

**What works.** All 10 judge-style prompts classified into the expected archetype on the first try and produced schema-valid documents with no repairs: 4/4 games were single-attempt winnable (sanity + win path), 4/4 scenes were objective-less explorable docs, and both edits applied as minimal, valid patches. The guard edit added a real second patrolling enemy; the campfire edit added three crystal entities. The classifier guidance and the explore few-shot from Task 5 carry natural scene prompts ("museum", "neon city street", "cozy reading room") reliably, and the explore edit prompt correctly stops the model from bolting an objective onto a free-roam scene. Latency was 5.4–36.6 s per stage, acceptable for a demo with the progress HUD.

**What's shaky.**

1. **"Add crystals to collect" is visual-only on an explore scene.** The edit added `crystal-[1-3]` as `prop` entities with no objective or pickup rule — the explore edit policy explicitly forbids adding objectives. A judge who then walks into a crystal and expects it to disappear will see nothing happen. The fix is a product decision (allow convert-to-game edits, or make the edit prompt turn them into interactables with `showMessage`); this eval deliberately did not weaken the explore policy to mask it.
2. **One sample per prompt.** Temperature is 0.2 but generation is still stochastic; one green run does not prove all ten prompts will behave identically on a judge's machine.
3. **"Solvable" is static, not simulated.** The win-path check proves a `win` action exists, not that a player can trigger it; activate-target reachability and rule-firing order are not simulated by `sanityCheck` (only collect/reach target pathability is). The docs are clean, but this is weaker evidence than a scripted playthrough.
4. **Edit reports are structural, not semantic.** The diff proves an entity was added and the archetype kept; it does not prove the added enemy state/rules make sense in every field.
5. **Latency tail.** The slowest generation (36.6 s) is near the edge of what a live demo should tolerate; the go gateway was stable (0 retries) but the spread is wide.
